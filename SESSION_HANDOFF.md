## Item 2 - `retrieval_core.run_rag_eval` has no context-overflow preflight

`run_eval.py` has `preflight()` (lines ~63-86) specifically because Q1 hit a
~23k-token question that exceeds `N_CTX=8192`; overlong questions become
`error` records instead of being scored. `retrieval_core.run_rag_eval` has no
equivalent - `fit_docs_to_budget` only trims the *retrieved documents*, never
the underlying question, so a bare question that already exceeds `N_CTX` still
overflows and crashes vLLM. Because the notebook shells out via
`subprocess.run(cmd, check=True)`, this aborts the whole Stage D loop (winner x
full panel x 3,600 questions - the most expensive run in the project) and will
recur identically on every retry.

Fix, respecting the "no copy-pasted logic; reusable logic lives in
`eval_core.py`" constraint:

1. Move `preflight()` out of `run_eval.py` and into `eval_core.py` (same
   signature: `(questions, tokenizer, scoring, n_ctx) -> (ok_questions,
   error_items)`). Update `run_eval.py` to call `ec.preflight(...)` instead of
   its local copy.
2. In `retrieval_core.run_rag_eval`, after building each question's
   `letter_user`/`logprob_stem` (which already include the RAG prefix), call
   `ec.preflight(questions, tokenizer, scoring, ec.N_CTX)` before scoring.
   Merge the resulting `error_items` into `per_item` as error records (same
   shape `run_eval.py` uses: `question_id`, `error: True`, `error_type:
   "context_overflow"`, `n_tokens_estimate`, `shuffled_gold`, `permutation`),
   the same way `run_eval.py`'s `main()` does.
3. In `retrieval_core.mcnemar`, guard against records that lack a `"correct"`
   key (exactly what an overflow/error record looks like) - skip them when
   building `b_map` and when iterating `per_item_a`, rather than letting a
   `KeyError` propagate.

## Item 4 - no cross-notebook permutation consistency check

Notebook 1 has an explicit tripwire (`_build_01_baseline.py`, shuffle section:
`assert ec.build_permutation_table(test) == perm_art["table"]`) that would
catch it if `eval_core.shuffle_options` were ever edited after the freeze.
`retrieval_core.py` has no analogous check - it re-derives shuffles on the fly
via `ec.prepare_questions(slice_ds, "zero_shot")` and compares against notebook
1's already-uploaded bare results via `mcnemar()`, trusting - with no
assertion - that `eval_core.py` hasn't drifted between the two runs. Both
sides already carry a `"permutation"` field per item, so the check is cheap.

Fix: in `retrieval_core.mcnemar`, when matching records by `question_id`, also
assert that `a["permutation"] == b_map_perm[question_id]` (track permutation
alongside `correct` when building the lookup from `per_item_b`) and raise a
clear error listing any mismatched question ids, rather than silently scoring
mismatched shuffles as if they were comparable.

## Item 5 - `shuffle_options` has a dormant non-determinism landmine

`eval_core.py`, `shuffle_options()`:
```python
q = int(example_id) if str(example_id).isdigit() else abs(hash(str(example_id))) % (2**31)
```
Python's `hash()` on a string is process-salted by default
(`PYTHONHASHSEED`), so if `example_id` were ever non-digit, the derived
permutation would differ across subprocesses and across notebook runs with
**no error raised**. Currently dormant because `_normalize()` always sets
`example_id = str(idx)` for the `lex_glue` path (always digits), but it's a
landmine if the data source ever changes.

Fix: replace the `hash()` fallback with a stable hash, e.g.:
```python
import hashlib
...
q = int(example_id) if str(example_id).isdigit() else int(hashlib.sha1(str(example_id).encode()).hexdigest(), 16) % (2**31)
```
(add `import hashlib` to the top of `eval_core.py`).

## Item 6 - Haiku 4.5 API retry-exhaustion looks like a parse failure

`eval_core.run_api_letter_emit`: when all 5 retries are exhausted on the
caught, retryable exceptions (`RateLimitError`, `InternalServerError`,
`APIConnectionError`), `resp` stays `None`, `raw=""`, `pred=None` - identical
in shape to the model genuinely failing to emit a parseable letter. The
resulting record is marked `completed=True` in the notebook's `run_api()` and
is never retried on rerun, and it silently blends into `n_parse_fail`.
(An uncaught exception type, e.g. `BadRequestError`, already crashes loudly -
that path is fine as-is; this fix is only for the exhausted-retryable-retries
case.)

Fix: when the retry loop exhausts without a `break`, build an error record
(`error: True`, `error_type: "api_failed"`, `question_id`, `shuffled_gold`,
`permutation` - same shape as the GPU-side overflow records) instead of a
normal per-item record. In the notebook's `run_api()`, split `per_item` into
valid vs. error records before calling `ec.compute_metrics` (mirroring
`run_eval.py`'s `main()`: `valid = [r for r in per_item if not
r.get("error")]`), then merge back with `metrics["n_error"] = len(error_items)`
and `per_item = valid + error_items` before saving.
